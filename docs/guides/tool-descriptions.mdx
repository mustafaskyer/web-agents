---
title: Writing tool descriptions
description: A model picks a tool, and the order of calls, from its description alone. Four things to say, how to describe parameters, and how answers and errors guide the next step.
---

An agent never sees your page the way the person does. It sees a list of tool names, descriptions and parameter
schemas, and decides from those alone which tool to call, with what, and in what order. A vague description is the
most common reason an agent calls the wrong tool or gives up.

## Say four things, in this order

One or two sentences each:

1. **What it does, and what it answers.** "Open one product's page and answer its price, sizes and stock."
2. **When to use it.** "Use after search_products or browse_category, when the user picks a product."
3. **What it needs first**, when another tool has to run before it or it only exists on some page. "Only on the
   checkout page (go_to_page checkout first)." "Needs the cart open (open_cart)."
4. **What comes next.** "Next: add_to_cart, which only exists on that page."

```ts
defineWebTool({
  id: "open_product",
  description:
    "Open one product's page and answer its price, sizes and stock. " +
    "Use after search_products or browse_category, when the user picks a product. " +
    "Next: add_to_cart, which only exists on that page.",
  // …
});
```

The same applies to declarative forms through `tooldescription`.

## Parameters say where a value comes from

Describe each parameter's source and format, with an example:

| Weak | Strong |
|---|---|
| `slug: the product` | `slug: the slug as search_products lists it, e.g. "ocean-tee"` |
| `date: date` | `date: the departure date, YYYY-MM-DD, e.g. 2026-11-20. For "next Friday", call get_time first.` |
| `qty: quantity` | `qty: how many to add, 1–20, e.g. 2` |

In zod, that's `.describe(…)`; on a form control, `toolparamdescription` (or its `<label>`).

## Answers point to the next step

A tool's answer is the agent's next prompt. Repeat the next step where it helps:

> Ocean Tee: $28, sizes S, M, L, in stock. Use add_to_cart to buy it.

## Errors say how to fix them

Give every failure a [code](/concepts/errors) and a message the agent can act on:

```ts
throw new WebToolError("invalid_input", 'No product matches "x". Try search_products with one key word.');
```

## Ask, don't invent

Tell the agent to ask for what the person didn't give, rather than guess. A description like "Ask for the travel date
if the user didn't give one" prevents a booking for an invented date.

## For small on-device models

Models of a billion parameters or less can't infer a site's flow from tool names. Give the
[on-device agent](/guides/on-device-agent#site-instructions) a few plain lines of site instructions on top of good
descriptions.

The example apps (`apps/ecommerce/src/tools`, `apps/flights/src/tools`) follow these rules throughout; they're worth
reading side by side with this page.
