title: The agent cursor
description: How the ghost cursor moves, waits for confirmation and gets out of the person's way, plus its options, the spotlight and how to restyle it.
---

The cursor is the visible half of `web-agents`. It shows _where_ the agent is working and _what_ it's typing, parks
where the person has to decide, and disappears the moment they move.

```ts
import { installAgentVisuals } from "@webmcp-agents/core";
import "@webmcp-agents/core/cursor.css";

const visuals = installAgentVisuals({ spotlight: true, name: "Assistant" });
```

In React, `<WebAgentsProvider visuals={…}>` does this for you, before its first tool registers.

## Options

| Option | Default | |
|---|---|---|
| `sync` | `true` | Hold the agent's values and submit until the cursor gets there, so the page reacts at the click. See [In step with the page](/concepts/how-it-works#in-step-with-the-page). |
| `spotlight` | `false` | Blur and dim everything except the tool being worked in. `true`, or `{ blur, dim, padding }`. |
| `yieldToUser` | `true` | Hide the cursor when the person interacts. `false`, or `{ moveThreshold, resumeAfter, ignore }`. |
| `linger` | `1200` | Milliseconds the cursor stays after a tool finishes. |
| `name` | `""` | A tag shown beside the cursor. |
| `log` | — | Receives every [agent event](/reference/core/on-agent-event). |

`installAgentVisuals()` returns `{ setSpotlight, setYieldToUser, destroy }`, so both switches can change at runtime
(the devtools' Settings tab is wired to them). Full reference:
[`installAgentVisuals`](/reference/core/install-agent-visuals).

## Yielding to the person

*The person moves the mouse while the agent is adding to the cart: the cursor vanishes and the tool still completes.*

A real person always wins. When they move the mouse more than a few pixels, click, scroll, touch or press a key, the
cursor, its tag and the spotlight fade out in 80 ms, and every pending step fast-forwards: moves arrive at once,
typing writes the final value, and a held submit or `execute()` runs immediately. **The tool still completes and
answers the agent**; it just stops waiting for the animation.

- Only trusted input counts. The agent's own fills never make the cursor yield.
- While the browser waits for a confirmation click, the ring on that button stays, so the person knows where to
  confirm.
- After `resumeAfter` ms (800 by default) without input, the next tool call shows the cursor again, entering from where
  the person's pointer was.
- Input inside an element marked with `data-web-agents-ui` ([`UI_HOST_ATTR`](/reference/core/ui-host-attr)) never
  counts: that's the person driving the agent from a chat or the devtools. Mark your own agent UI the same way.

*The agent fills checkout and the cursor parks on Place order until the person clicks it.*

Two kinds of tool make the agent wait for the person:

- a **declarative form without `toolautosubmit`**: the browser pauses on its submit button;
- a **`WebTool` with `requireConfirmation: true`**: the call waits for a trusted click on the tool's element.

Either way the cursor parks on the button with a "Click … to confirm" prompt. The person's click is the only thing
that completes the call. See [Tools](/concepts/tools#asking-for-confirmation).

## How it moves

<video autoPlay loop muted playsInline data-no-zoom width="960">
  <source src="../media/cursor/typing.webm" type="video/webm" />
  <source src="../media/cursor/typing.mp4" type="video/mp4" />
</video>

*Minimum-jerk travel, a spring on arrival, the values typed in place.*

One `requestAnimationFrame` loop drives everything, and every animation uses transforms and opacity only.

- **Curved paths.** The target point travels an arc with a minimum-jerk profile, the curve a human reach follows.
  The arrow chases it on a near-critically-damped spring, so a new move mid-flight bends the path instead of
  restarting it.
- **Fitts's-law timing.** Travel takes 180 to 650 ms depending on distance and target size, and each step waits for
  _arrival_, not a fixed delay.
- **Anchored to the page until the click.** On the way, positions are re-read every frame, so the cursor rides along
  with scrolling and layout shifts. After the click it stays put, even if the action moves the button.
- **At rest** it sways gently around its tip, a little more while waiting for the person.
- **Reduced motion.** Under `prefers-reduced-motion`, everything snaps and fades.

Tool status is also announced in a polite live region for screen readers.

## Spotlight

`spotlight: true` blurs and dims the page except the tool being worked in (the nearest `[toolname]` element, such as a
whole product form), and the clear window glides from tool to tool. Tune it with
`spotlight: { blur: 4, dim: 0.08, padding: 12 }`. It never takes pointer events, so the person can still click to
confirm.

## Styling

The cursor is a black multiplayer-style arrow with a white edge, readable on light and dark surfaces. Its colours are
custom properties at the top of `@webmcp-agents/core/cursor.css`:

```css
:root {
  --agent: #111111;        /* fill for the arrow and the tag */
  --agent-ink: #ffffff;    /* text on the tag */
  --agent-strong: #111111; /* outlines, rings and borders */
  --agent-wait: #111111;   /* while waiting for the person to confirm */
}
```

To brand it, override them after the import: `:root { --agent: #4f46e5; --agent-strong: #4338ca; }`.

See [`cursor.css`](/reference/core/cursor-css) for every class and state.

:::warning[Don't use showModal() for drawers]
The top layer of a modal `<dialog>` hides the cursor (and makes the devtools inert). Use a non-modal
`role="dialog"` panel and make the page behind it `inert` instead, as the [examples](/examples/field-store) do.
:::
